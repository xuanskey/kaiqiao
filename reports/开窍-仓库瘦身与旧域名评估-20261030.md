# 仓库瘦身与旧域名横幅：评估（只评估，未改动）

日期：2026-10-30。两项都等杨哥确认后再动手；本报告不改代码、CI、Cloudflare 或 DNS。

## 一、旧域名横幅 `domain-transition.js`

### 结论

**先别删。** 删掉它救不回任何用户，也省不了多少维护成本；真正要决定的是要不要在 Cloudflare 暂停裸域 301，而不是删不删这段代码。

### 现状（事实）

- `site/www.yanghat.cn/domain-transition.js` 只处理**裸域 `yanghat.cn`** 的顶层页面：本机有练习记录 → 显示「先导出备份」横幅；没有记录 → 跳到 www。它**不处理 `kaiqiao.yanghat.cn`**，那个子域的页面根本不加载这个脚本。
- `site/README.md`「旧域迁移」记录：2026-10-30 实测裸域被 Cloudflare 规则 301 到 www，发生在页面脚本运行前，所以横幅和保护性跳转在线上都不会触发。
- 依赖它的地方：`site/www.yanghat.cn/index.html` 首个脚本、`_headers` 缓存规则、`scripts/check-site-cache.mjs`、`scripts/check-domain-transition.mjs`（在 `npm run test:site` 中，CI 的 site job 会跑）、`src/lib/math/domain-transition.test.ts`。删除需要连带改 5 处，并重新 release。

### 有没有真实用户（推测，无法从仓库证实）

- 现有统计**分不出裸域和 www**：`workers/metrics/handler.js` 把 `yanghat.cn` 和 `www.yanghat.cn` 都记为 `prod`。所以 AE 数据回答不了这个问题。
- 能回答的数据源：Cloudflare 后台 yanghat.cn 区的 **Analytics → Traffic**，按主机名看 `yanghat.cn` 与 `kaiqiao.yanghat.cn` 在 301 生效前的请求量；或 Pages 项目的 Web Analytics（如开过）。
- 本机存储按源隔离：如果当时确有家长在裸域或 kaiqiao 子域练过，他们的记录现在仍留在各自浏览器里，但因 301 打不开那个源的页面，**无法导出**。

### 三个选项

| 选项 | 做法 | 收益 | 风险 / 成本 |
| --- | --- | --- | --- |
| A. 保持现状（推荐，在查到流量前） | 不动代码，不动 Cloudflare | 零风险；以后要暂停 301 时保护逻辑现成可用 | 首页多一个 1 KB 的 no-cache 脚本请求 |
| B. 暂停 301 一段迁移期 | 管理员在 Cloudflare 暂停裸域 301（步骤见 `site/README.md`），2–4 周后恢复 | 有记录的旧用户能看到横幅并导出 | 需要 Cloudflare 操作；迁移期裸域与 www 并存，依赖 canonical 头防 SEO 重复 |
| C. 确认无真实用户后删除 | 删脚本及 5 处引用，重新 release | 少一个请求、少一套测试 | 一旦判断错，旧用户数据永久无法通过页面导出 |

需要杨哥决定：去 Cloudflare 看 301 生效前 `yanghat.cn` / `kaiqiao.yanghat.cn` 的请求量。几乎为零 → 选 C；有一定量 → 先 B 再 C。

## 二、仓库瘦身

### 结论

**值得做，但只做「停止新增」，不改写历史。** 收益主要是 PR diff 干净和 clone 变快；构建产物目录 `docs/` 是 release 脚本和 CI 的硬依赖，改动必须连同 CI 一起做，建议单独一个 PR。

### 现状（2026-10-30 测量）

| 路径 | 工作区大小 | 入库原因 / 依赖 |
| --- | ---: | --- |
| `docs/` | 19 MB（其中 `docs/ocr/` 15 MB，`offline.html` 760 KB） | `npm run release` 生成；README「可以把 docs/ 部署到静态网页服务」；CI verify job 跑 release 后 `git diff --exit-code -- docs/`，site job 再查 `docs/ site/` 无改动 |
| `site/www.yanghat.cn/app/` | 19 MB | `npm run build` 同步的完整应用；正式部署直接上传 `site/www.yanghat.cn/`；`deploy:site` 护栏拒绝 site/ 未提交改动 |
| `site/www.yanghat.cn/assets/` | 7.7 MB | 宣传片 MP4、海报等源素材，非构建产物 |
| `reports/` | 7.0 MB（40 张 PNG，`home-simplify-shots/` 一个目录 4.9 MB） | 历次验收截图与日志 |
| `.git` | 27 MB（pack 25.5 MB） | 历史中 docs/ 相关 blob 约 55 MB（未压缩，与 site/app 大量同内容去重） |

- 每次改应用源码都要连带提交 docs/ 与 site/app/ 的整批哈希文件（本 PR 也是如此），PR diff 里大部分是产物。
- `docs/ocr/` 与 `public/ocr/` 是同一套 OCR 模型，git 按内容去重，不重复占历史空间，但每次 clone 都要下载。

### 方案对比

| 方案 | 做法 | 收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| 1. 截图移出（低风险，推荐先做） | 新增 `reports/**/*.png` 到 `.gitignore`，以后截图作为 PR 附件或 Release 资产；已有截图保留 | 每轮验收不再加几 MB | 无代码影响；旧报告里的图片链接不变 |
| 2. docs/ 不再入库 | 删 `docs/` 跟踪 + `.gitignore`；CI 的 `git diff -- docs/` 改为「release 成功且产物齐全」检查；README 的「docs/ 部署」改为从 Release 附件或本地 release 获取 | PR 不再带产物 diff；新 clone 少 19 MB | 要改 `check.yml` 两处、README，以及读 docs/ 的 `scripts/bundle-size.mjs`、`scripts/check-offline-classroom.mjs`（改为读 release 刚生成的目录即可，仍可在 CI 里先 release 再检查）；GitHub Pages 若指向 docs/ 会失效（需先确认没在用） |
| 3. site/app/ 不再入库 | 部署前在 CI 或本机 release 生成 | 同上，再少 19 MB | 部署护栏要求 site/ 已提交、Cloudflare Direct Upload 是本机上传；需重新设计「上传的就是审过的」保证。**不建议现在做** |
| 4. 改写历史（filter-repo） | 从历史中剔除 docs/、截图 | .git 可降到几 MB | 所有 clone、PR 链接、提交哈希（含许可边界 main@17a25022）失效。**不建议** |

### 建议顺序

1. 先做方案 1（只改 `.gitignore`，几分钟）。
2. 确认 GitHub Pages 未使用 `docs/`、离线包从哪里发给家长后，再单独一个 PR 做方案 2，连同 CI 一起改并在 PR 里跑通。
3. 方案 3、4 暂不做。

需要杨哥确认：(1) `docs/` 是否还被 GitHub Pages 或其他地方直接引用；(2) 家长下载离线包的渠道（docs/offline.html 链接还是 Release 附件）。
